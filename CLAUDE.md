# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the Vite dev server
- `npm run build` — production build to `dist/`
- `npm run preview` — preview a production build locally
- `npm test` — run the Vitest suite once (`vitest run`)

There is a test suite. `src/lib/financials.test.js` covers `src/lib/financials.js` with hand-computed expectations; run it before reporting any calculation change complete. The same module is also covered by `import.test.js` (the file reader: date order, headers, layouts, encodings, repeated rows, closing balance), `kinds.test.js` (transfers, loans and owner money, refunds, and the founder's rules), `months.test.js` (partial months and period starts) and `cash.test.js` (the saved cash balance, overdrafts and stale balances) and `runway.test.js` (current burn, cash today and what runs on them). `src/lib/one-time-products.test.js` imports `supabase/functions/_shared/one-time-products.ts` directly — the exact code the Edge Functions run to judge captured money — which works because that module has no imports and no Deno APIs. Keep it that way, or the server's payment checks drop out of test coverage. `src/lib/subscription-entitlement.test.js` does the same for `supabase/functions/_shared/subscription-entitlement.ts`, under the same rule, and `src/lib/payment-events.test.js` for `_shared/payment-events.ts`. `src/lib/payment-webhook.test.js` is the payment acceptance suite: it runs `_shared/paypal-events.ts` and `_shared/paypal-access.ts`, the code the Edge Functions run, against a simulated PayPal and database, so those two must stay free of Deno APIs and remote imports too. It proves the logic, not that PayPal delivers real events; only a real payment shows that. `src/lib/import-verification.test.js` is the import acceptance suite: every rule below under **Verified imports**, with hand-worked answers, plus `_shared/verification-brief.ts`, which must stay free of Deno APIs for the same reason. `src/lib/file-currency.test.js` covers reading a file's currency. `src/lib/coverage.test.js` covers account answers, statement coverage per account and D1's 3-month window (correction plan, Phase 1 task 3), with the plan's worked examples. `src/lib/affordability.test.js` covers the two affordability tests and the order in which an answer is given or held, `src/lib/bills.test.js` covers bills that cannot be checked, and `src/lib/judgements.test.js` covers everything that reads the last 3 calendar months (hiring capacity, both break-evens, the risk floors, the scenario, the ordered findings, unidentified money that could reverse a loss, the month in progress, missing months, uncategorised costs, growth between levels). `src/lib/advisor.test.js` covers the AI advisor's contract (Project 3): the eleven scenarios of `src/lib/advisor-scenarios.js` run through the Dashboard's own pipeline with hand-worked evidence, the server's rebuilding of what the browser sends, and every check on a reply, using fixed replies written by hand (never model output). It imports `supabase/functions/_shared/advisor-contract.ts` directly, which must stay free of Deno APIs and remote imports for the same reason as the modules above. `src/lib/advisor.eval.test.js` is the real-model evaluation: `npm run eval:advisor` sends the same scenarios to Claude through the exact server code and writes every brief to `ADVISOR_EVAL_OUT`; it needs `ANTHROPIC_API_KEY` or `ANTHROPIC_AUTH_TOKEN` in the environment, costs money, and is reported as skipped (never passed) under a plain `npm test`. `src/lib/currency.test.js` covers money formatting, amount parsing (comma decimals, Cr/Dr, currency markers) and mixed-currency files; `src/lib/workspace.test.js` also reads `App.jsx` and fails if any `fmt(`/`fmtCompact(` call omits its currency. There is still no lint script; if you add one, wire it into `package.json` and update this section. Test settings live under `test` in `vite.config.js`: `src/lib/test-setup.js` warms up `Intl` and WebCrypto before any test is timed, and `testTimeout` is 30s. Both exist because the first test in a worker absorbed several seconds of runtime start-up on slow 2-core machines and failed intermittently against Vitest's 5s default (a plain `fmt(1250)` once took 7.4s). Don't remove either as clutter, and don't paper over a new timeout with a command-line flag.

**`xlsx` is installed from the vendor's CDN, not the npm registry.** SheetJS stopped publishing to npm after 0.18.5, which carries an unpatched prototype-pollution and a ReDoS advisory, so `package.json` pins `https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz`. A fresh `npm install` therefore needs `cdn.sheetjs.com` to be reachable. Do not "fix" this back to a registry range — that silently reintroduces both advisories.

Supabase Edge Functions are deployed with the Supabase CLI via `npx` (it isn't installed globally in this repo). Pass `--use-api`: without it the CLI waits on Docker and hangs. `paypal-webhook` also needs `--no-verify-jwt`, or PayPal's calls are refused before they reach the code. On a slow connection a deploy can fail with a TLS timeout; run it again, and confirm the version went up.

```
npx supabase functions deploy <function-name> --project-ref rjecagelwzorklmnscrr --use-api
npx supabase secrets list --project-ref rjecagelwzorklmnscrr
npx supabase secrets set KEY=value --project-ref rjecagelwzorklmnscrr
```

Database schema lives in `supabase/migrations/` and is applied with `npx supabase db push --linked`. `npx supabase migration list --linked` compares local to remote. The `profiles` table predates these migrations and was managed by hand on the remote project; its entitlement columns (`status`, `updated_at`) and its plan guard now live in migration `20260913010000`. **`profiles.plan` has no default and must never be given one** — it carried `DEFAULT 'essentials'` until `20260913020000`, which entitled every inserted row that did not name a plan. The guard trigger `guard_profiles_plan_status` fires `BEFORE INSERT OR UPDATE` and resets `plan`/`status` for the `anon` and `authenticated` roles; only `service_role` (the webhook) and direct database connections can set them.

**Code was written against `profiles` columns that did not exist, and nothing noticed for months.** The webhook wrote `status` and `updated_at`, the AI advisor selected `status`, and sign-up wrote `updated_at` — none of which the table had. PostgREST rejected every one of those requests, so no subscription could grant access, the advisor refused every user, and new profile rows were never created. Two lessons follow. **Before shipping code that reads or writes a column, confirm the column exists** (`information_schema.columns`). And **never discard a Supabase `error`** — each of these failures was silent only because the error was ignored or a fallback hid it. A third: **PostgREST returns at most 1,000 rows per request and does not say so.** Reading transactions in one request gave any business with more than 1,000 in the period only its oldest 1,000, silently dropping the latest months; `selectAll()` in `App.jsx` pages through every row, and any new bulk read must use it.

Two CLI quirks worth knowing: there is **no `functions logs` subcommand**, and `secrets list` prints digests only, never plaintext.

## Architecture

**The entire application is one file.** `src/main.jsx` just mounts `src/App.jsx`, which contains the marketing site, auth flow, dashboard, all React components, and all CSS (as an inline template-literal string assigned to `CSS`) — around 2,800 lines. **A stray backtick anywhere inside the `CSS` template literal terminates the string and breaks the build**, so never use backticks in its comments. **Every class in `CSS` is global**, so a new class can collide with a marketing-site rule: a KPI tile once used `hero` and inherited the marketing hero's `min-height:100vh`. Grep for an existing `.name{` before introducing a class.

**Design follows `DESIGN.md` and `UX-CONTRACT.md`; read both before any visual change.** Colour tokens are defined once in the `:root` block at the top of `CSS`, sampled from the brand mark, and the `C` object maps each to `var(--token)` for inline styles, so no component hardcodes a colour. **`assets/Logo.png` is the final brand asset**: never crop, recolour, redraw or generate alternatives; `public/brand/` and the favicons are the same image scaled only, and `BrandMark` picks the right copy. Public-site classes use the `mk-` prefix. No em or en dashes in any user-facing copy.

The one exception to the single-file rule is `src/lib/financials.js`, which holds every pure calculation and parsing function. New financial logic belongs there, not in `App.jsx`, because that is the only part of the codebase under test. There is no router; navigation is a single `appState` state machine in the top-level `App()` component (`loading` → `marketing` / `login` / `dashboard` / `terms` / `privacy`), and `Dashboard` vs. `PaywallGate` is chosen based on whether `profile.plan` is set. Inside the signed-in workspace, `Dashboard` is an app shell (sticky header with search, alerts, period selector and account menu; a sidebar that becomes a drawer below 960px) with nine sections, each at its own path (`SECTIONS` in `App.jsx`: `/dashboard`, `/transactions`, `/financials`, `/advisor`, `/reports`, `/decisions`, `/forecasts`, `/settings`, `/help`). `useSection()` reads the path on load, `pushState`s on navigation and listens for `popstate`; there is no router dependency. A signed-out visitor on a workspace path is sent to `/`. Two public pages have their own paths, `/terms` and `/privacy` (`LEGAL_PATHS`), so search engines can index them and payment providers can link to them; `App` writes each page's `<title>` and canonical link after rendering, because the single `index.html` cannot know the path (do not put a static canonical back in `index.html`: it would point `/terms` at the home page). `vercel.json` sends `X-Robots-Tag: noindex` on every extension-less path except `/`, `/terms` and `/privacy`, which keeps the workspace and every unknown path (the SPA rewrite answers those with 200) out of search. A new public page needs its path excluded from that rule and added to `public/sitemap.xml`. `Dashboard` loads data and derives every metric once, then hands sections a single `ctx` object, so a number shown on two pages cannot disagree. Header search (`searchWorkspace`), the alerts bell (`buildAlerts`) and the Reports CSV (`buildReportCsv`) are pure functions in `financials.js`, tested in `src/lib/workspace.test.js`. The Reports key metrics and the CSV summary are one list, `buildReportSummary()`; while `profitHold(m)` names a hold (`figuresOpen`, or `vatHold`), every profit-basis figure there, in both monthly tables, the capital allocator and the dashboard chart's net shows `---` (`held` in the CSV) with the reason, as on the tiles (`src/lib/reports.test.js`). It once printed a held R120,000 loss as Net profit.

**Auth and plan-gating run through Supabase.** The Supabase client is created at module scope with `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`. On sign-in, `loadProfile()` reads (or upserts) a row in the `profiles` table; a falsy `profile.plan` routes the user to `PaywallGate` instead of `Dashboard`. Access control is entirely driven by `profiles.plan` — there is no separate entitlements table.

**A file's currency is read from the file.** `detectFileCurrency()` looks for what the file states (a Currency column, R or $ on the amounts, ZAR in a money column's heading, a line above the table), then for what its details show (two or more South African or US clues, the file's own bank counting double), and returns null when nothing proves it. Many bank exports are plain numbers, so null is normal. `resolveFileCurrency()` then decides: the founder's own choice, the file, the business currency (the upload says it did this), or one question if there is none. It must never default to dollars, and anything not stated outright says so in the upload message with where to correct it, because a wrong label gives wrong figures with no warning. With no transactions on file, the first file sets the business currency.

**Verified imports.** Nothing is saved until the founder confirms it on `ImportReview`. `verifyImport()` (`financials.js`) gives two separate answers: `importStatus` (`accepted`, `rejected`) and `reconciliationStatus` (`verified`, `not_reconciled`, `failed`). `verified` means only that the file's own balances agree with its own transactions, to the cent (`expected = previous balance + amount`, `reconcileStatement()`); it is never bank confirmation, and figures are never adjusted to agree. A file with no usable balance is accepted only if its layout and direction of money are safe, and is marked `not_reconciled` with `NOT_RECONCILED_MESSAGE`. A file that fails its balances cannot be saved. Refused outright: unreadable dates or amounts, unsigned amounts with no direction, two possible amount columns, card statements, ledgers with no balance to prove direction, dates whose order cannot be settled, and an unknown currency. The balance column decides what a layout leaves open, and a reading is used only when every balance agrees: a Fee column inside money out (`feesIncluded`) and a ledger's Debit as money in (`debitIsMoneyIn`). The status is stored on `upload_batches` (`import_status`, `reconciliation_status`, `reconciliation_detail`, `account_label`, migration `20261107221608`, applied 2026-11-07). A row with no status is an older upload and reads as `not_reconciled`. `summarizeVerification()` looks only at files contributing to the figures on screen, and one unreconciled file makes the whole `not_reconciled`; `VerificationNotice`, the report, the CSV and the AI brief all carry it. `analyze-finances` removes any claim of verified figures in code (`guardVerificationClaims`), not only in its prompt. Whatever the status, it also removes any claim of bank confirmation ("bank-verified", "confirmed by the bank"), because Command Ledger has no bank connection, and any claim that estimated cash is verified, reconciled or confirmed; "reconciled" may only mean a file agrees with its own balances. It catches the word "bank", not bank names. There are no session-only figures: an unsaved file shows nothing outside the review. Review choices become rules through `reviewRuleRows()`: one rule per description, because Postgres refuses a whole upsert that touches one row twice and every choice in the file would be lost. Choices that disagree are both left out and the founder is told, never guessed. A test double accepted both this and an over-long account name, so check a save path against the live table's constraints, not only a fake.

**Money in nobody has identified.** A transaction marked `reviewed` (from a batch with a status, not a monthly summary) that would be operating money in counts as revenue only if `looksLikeRevenue()` says so or the founder sets a rule; otherwise its kind is `unconfirmed`: in no figure, totalled in `unconfirmedIn`. It is not a rule kind and is never stored. Older uploads keep their first reading. `REVENUE_WORDS` holds only words a customer payment carries, never words a bank prints on any incoming row (settlement, receipt, credit, deposit): Absa puts "Settlement" on every PayShap line, and that once counted 83% of a real statement's money in as revenue while every invented test passed. Test classification against real statements, not only fixtures. `verified` proves a file agrees with itself, not that it is complete: a statement cut short still reconciles unless it states its closing balance. Unconfirmed money is a gap, not a zero: at 10% or more of money in (`figuresOpen`, `UNCONFIRMED_MATERIAL_SHARE`, a judgement set by hand) profit, margin, runway, risk, hiring capacity, the projection, scenarios and affordability show `---` or wait, the AI advisor does not run (`runAI` returns first, because its brief would carry the loss the screen holds back, and a prompt line is not a guard), and the directive asks the founder to confirm the money. Counted as nothing, it read a real account with a R154.65 surplus as a R5,662 critical loss. Banks list rows with no money and no balance (declined attempts) and pending rows; both are left out and shown, and a row with no amount is only safe to leave out when a running balance proves nothing moved.

**Statement coverage and account answers.** No upload records a statement period (`period_start`, `period_end` and `closing_balance_on` are transaction dates), so `accountCoverage()` marks every calendar month, per account, complete, partial, quiet or gap, and a month with no transactions is a gap, never zero, unless the founder confirms it in `account_answers` AND a verified balance is unchanged across it (inside one verified file, or between two verified files of the same account); balance evidence alone is only a note (`coverageNote()`). A named upload's account is `accountKey()` of its name; an unnamed upload is its own account, `upload:<batch id>`, until the founder links it. No answer means unresolved, never closed; only a `closed` answer with its date ends an account. A `same_as` link to an account no longer on file, or a loop, is ignored and leaves every account in that chain unresolved and apart. A business month is a gap when any account expected in it is one. Answers are saved only through `accountAnswerRows()`, which sends every field (an upsert keeps any field it omits, and the table's checks then refuse the row) and refuses one slot twice in a save (Postgres refuses the whole upsert). `judgementWindow()` is D1's window: the 3 calendar months ending with the latest month that has ended (on 15 July, April to June), whatever the statements cover. A missing recent month is a gap inside it, and the window never moves back to step round it (founder's decision, 2026-11-14). Runway's run rate and affordability use the same three calendar months: `runRateRowsWithQuietMonths()` adds each business month that is quiet (confirmed by the founder for every account expected that month, with a verified balance unchanged) to `currentRunRate()`'s rows as a month of zero; every other empty month stays out, never zero, and a quiet month is never added when no month of transactions is complete, so it cannot stand in for burn alone (founder's decision, 2026-11-14). With the coverage reading (`context.window` and `context.coverageMonths` in `computeMetrics()`, which the Dashboard always passes) burn is measured on that window (D10b, `window.measure`): from its months that are complete or quiet; with a gap, a part month or an overlap in it, at least 2 are needed, runway is low confidence and names the month left out, and with only 1 burn is held (`burnGap`: runway, hiring capacity, break-even, the risk score and scenarios show `---`). Without a window (older callers, manual entry) `currentRunRate()` is used as below. **Linked accounts that overlap are held, never de-duplicated by guess:** duplicates are matched per account name, so when the founder links two names whose own date spans overlap (two unnamed uploads excepted, since those were matched at upload), the months both cover get status `overlap`, their business totals are null and any 3-month judgement waits until one upload is deleted or the accounts are separated (`overlapWords()`).

**One ordered list of findings.** `computeFindings()` returns what is true of the business now, most serious first, on the last 3 calendar months; `computeMetrics()` returns it as `findings`, the directive is the first, and the dashboard headline shows the same one, so they cannot disagree. A loss is critical only with under 3 months of runway or cash gone, a warning at 2% of revenue or more and "near break-even" below that (D5, stored as `warn`). The latest complete month 20% or more below the average of up to 3 before it is a warning (D6). One client above 60%, measured over the last 12 complete months on every view, is critical only when the business could not last 3 months without it (D7). Growth that was not measured makes no growth claim. The risk label is never milder than the first finding, runway under 3 months or no cash while burning is Critical, and a business burning with no usable balance has no score at all (`risk.score` null with `risk.unknown`): less data must never read as safer. Unidentified money holds the figures at 10% of money in or when it is at least the size of the loss (`couldReverseLoss()`, D9): more money in cannot turn a profit into a loss, so a profit is not held by it under 10%. A cost category nothing matched is not known, not zero, while any cost is uncategorised (`uncategorised`, `cogsKnown`, `mktKnown`). No finding recommends extra spending (founder's decision, 2026-11-20): the calm-state directive (`stable_foundation`) and `scale_window` ask the founder to review lead generation and to test any growth cost with the affordability check; they once said "Increase lead volume by 20%" and "30%".

**Affordability.** `checkAffordability()` tests 12 monthly payments (the first on the start date, each on the same day or the last day of a shorter month) against cash today, D1's window and bills on their dates. A cost is affordable only if cash stays above zero and never falls below the floor: one month of everything that left the bank in the window plus the new cost. The checks run in a fixed order and the first that applies decides; a held answer names what is missing and is neither a pass nor a fail. It reads only the window, never `currentRunRate()`.

**Bills.** `detectRecurringObligations()` never ends a bill, and `detectMissedObligations()` returns `cannot_check` entries, never missed alerts, because nothing confirms a statement covers a due date. Only the founder ends a bill, and can mark it active again.

**Tax and VAT (defect 8, migration `20261115152456`).** Profit and cash are never mixed. Every monthly row carries both: `revenue` and `expenses` are cash, as it moved, and feed burn, runway, cash today, cash break-even and affordability, which no tax label can change; `profitRevenue` and `profitExpenses` are the profit basis, which revenue, costs, profit, margin, the reserves, the monthly result, hiring capacity and operating break-even read. Three rule kinds only the founder sets, never wording on a bank line: `income_tax_current` (income tax for the tax year it was paid in), `income_tax_prior` (for an earlier year) and `vat` (paid to or refunded by SARS). None is a cost on the profit basis; PAYE, UIF and SDL stay payroll costs and every other SARS payment stays a cost. Income tax is marked one payment at a time (`scope` single, enforced in `kindRuleRow()`, `buildRuleIndex()` and the table), and choosing "every transaction like this" never deletes an income tax mark. A payment whose description names SARS and has no rule is listed by `taxQuestions()` and stays a cost until answered, with nothing pre-selected. **The tax reserve is rolling:** the mode's rate on the period's profit before income tax, and payments never change it. **Tax year to date** (`taxYearToDate()`, `taxYearNote()`) is the only place payments are compared with a reserve: from the first month of the tax year (`profiles.financial_year_end_month`, no default) to the latest complete month, the same on every view, and not worked out without the year-end or when a month from the start of the tax year is missing. Its wording never says credit, refund due, overpaid or owed, and always says it is an estimate, not a SARS calculation. **VAT** is asked of rand businesses only (`profiles.vat_registered`, `vat_registered_from`, no default): unanswered, profit figures wait (`vatHold`), cash figures do not, and the advisor does not run. Every figure built on profit waits with it (founder's decision, 2026-11-20): hiring capacity (`hiringCapacityConfidence`), operating break-even (`operatingBreakEvenConfidence`, separate from cash break-even, which stands), the 3-month result and margin, and the risk score (`risk.score` null with a VAT reason), on the Dashboard, Reports, the CSV, Financials and the Advisor's evidence (`src/lib/reports.test.js`). For a registered business, amounts dated from the registration date are divided by 1 + `VAT_RATE.rate` (one named value, 15% since 2018-04-01; earlier dates are not divided) only where the founder's `vat_class` on the rule says so: money in `standard`; costs `claimable`. `zero_rated`, `exempt`, `not_claimable`, `no_vat` and `partly_claimable` count whole. A class that does not fit the direction of the money is not used. Anything unclassified takes the reading that gives the lowest profit, shown as "at least" (`profitRange`), and when it could turn a profit into a loss or a loss into a profit the profit figures are held. Every rule save goes through `kindRuleRow()`, which always sends `vat_class`: an upsert keeps a field it omits, and the table refuses a class left on a transfer. `src/lib/tax.test.js` holds the plan's worked examples. Trends, growth and seasonality still read cash revenue.

**Duplicates are per bank account.** `dedupeHashInput()` adds `|acct:<key>` when the upload names an account; with no account the hash is unchanged, so stored rows still match. `compareWithStored()` checks both forms, and warns when rows match another account, because the same file saved under two names would count twice.

**One file reader.** `parseTransactions()` reads every upload and the public demo (`parseAnyCSV()` wraps it): `decodeTextFile()` takes bytes (UTF-8 or UTF-16, with or without a BOM), the delimiter is detected, the header row is found within the first 25 rows, and headers map by exact name, then whole words (`HEADER_ROLES`, `HEADER_WORDS`). Numeric dates are read day first or month first from the whole column (`detectDateOrder`); a column that never settles it is read day first and the upload says so. Excel date cells are converted from their day count, never through a time zone. An identical repeated row gets `occurrence` 2, 3 and so on, which `dedupeHashInput()` adds to its hash; the first keeps the original form so stored hashes still match, and `occurrence` is never sent to the database. A Balance column gives the file's `closingBalance`.

**Transaction kinds.** Every transaction is `operating`, `transfer` (between the business's own accounts), `financing` (loans received or repaid, money the owner puts in or takes out) or `refund`. Revenue is operating money in less refunds paid; expenses are operating money out less refunds received; transfers and financing are kept in their own totals (`financingIn/Out`, `transferIn/Out`). Financing out is not a cost, so margin and profit leave it out, but it empties the bank, so net burn is costs plus financing out less revenue, over the last 3 complete months, and hiring capacity and the forward runway take it out too. A loan received never offsets burn. Concentration counts operating income only; recurring bills are operating and financing outflows only. The kind is worked out on every read and never stored on the transaction: a founder's rule in `transaction_rules` wins (`scope` "single", by `dedupe_hash`, beats "similar", by `classificationKey()`, the description with digits removed), otherwise `classifyTransaction()` reads the description. Its patterns match only unambiguous wording, because a wrong guess removes real revenue: a bare "transfer" is not a transfer, "loan" is singular so "Lakeside Loans" stays a customer, interest and fees stay costs, and bank names such as "First Savings Bank" are taken out first. Choosing "every transaction like this" deletes the single rules with the same `description_key`.

**Partial months.** `aggregateTransactionsByMonth()` marks a month `partial` when it is this month (by `options.today`) or when the data starts or stops more than 7 days inside the first or last month; a last month dated only on the 1st after another such month is a monthly summary and complete. Profit, margin, both reserves and profit after reserves are measured over complete months only (D4): a part month is reported beside them as `toDate` ("to date"), because on the 9th a month holds its takings and not yet its bills. Until one month is complete the part months are all there is, and they are used. Part months never count in the averages, latest month, growth, trends, seasonality or projection either. A month's change against the one before is measured only between neighbouring calendar months (`consecutiveTail()`), and is not known across a gap (`velKnown`). `monthLabel()` adds "(to date)" everywhere a month is shown, including the report CSV. The period filter starts on the 1st (`periodStartDate()`), so the first month is never cut short by the filter.

**Cash balance.** Runway is measured from a saved, dated balance: one the founder enters (`profiles.cash_balance`, `cash_balance_on`, `cash_balance_currency`, all three or none) or the closing balance of an upload with a Balance column (`upload_batches.closing_balance`, `closing_balance_on`). `effectiveCashBalance()` uses the newest in the business currency; on the same date the founder's own wins. A file's balance is one account's, so the founder's figure is how several accounts are totalled. A known balance of zero or below is real: runway is 0 (never negative), the runway directive fires, the forward runway is not run, and affordability says there is no cash for a new cost. A balance more than 45 days old lowers runway confidence one level. The session-only cash field was removed.

**Runway is estimated cash today divided by current monthly burn.** Burn is the last 3 complete months of the whole history (`currentRunRate()`), whatever period is on screen, and is rounded to the cent (`toCents`): a business that broke even exactly once read a rounding leftover as burn and showed 3.4 quadrillion months. With no complete month, a part month is not a month: burn is measured per day across the days the data covers (`coveredFrom` to `coveredTo`) and scaled by 30.44, only across at least `MIN_DAYS_FOR_DAILY_RATE` (28) days, at low confidence; under that, `burnShort` holds runway, the cash estimate, the forward runway, affordability and "No burn" alike, because a 30-day statement from the 10th once read as half a month of burn and twice the runway. Because burn reads the whole history, `loadHistory` reads every transaction once and the period is a filter in the browser. Averaging over the selected period showed 16.9 months for a business with 7.5 left, gave one business three runways, and passed a cost that would have run it dry. Cash today (`estimateCashToday()`) is the balance, plus what is recorded since (`cashMovementSince()`, transfers left out, unidentified money in), less burn for the days with no data; `cashTodayNote()` shows the working. Only a loss is estimated, never income. An overdraft the records prove is real and reads 0 months. One only the estimate reaches, or a gap over `MAX_ESTIMATED_DAYS` (90, a judgement set by hand), is `usable: false`: runway shows `---` and asks for today's balance rather than announcing the money has gone. Whether burn can be trusted is judged on those same 3 months (`burnOpen`), by the 10% line, not on the period on screen: judged on the period, one business read 15.0 months in one view and `---` in another. `figuresOpen` still governs the period's own totals. There is no safety share: runway is the published formula in both modes. The forward runway and `checkAffordability()` take `runRev`, `runExp` and `runFinOut`, so they cannot disagree with it. Hiring capacity, operating break-even (`breakEven`, costs on the profit basis) and cash break-even (`cashBreakEven`, every outflow net burn counts, so money in less it is always minus net burn) read the same months as burn, whatever period is on screen (D1, D8). Scenarios start from `runRev`, `runExp` and `runFinOut` too, with the dashboard's own trends and client share carried in (`options.base`), so "before" is the dashboard's runway and risk. Known limits: three months can read short in a slow season and long in a busy one, and a balance covering several accounts is rolled forward only by the accounts uploaded.

**Financial metrics are computed client-side, not stored.** `computeMetrics()` in `src/lib/financials.js` derives margin, burn runway, LTV:CAC, break-even, a 90-day projection, a trend-aware composite risk score, growth scoring with a seasonality override, revenue concentration by counterparty, and forward obligations — from either parsed rows (`parseAnyCSV`, `parseTransactions`, `detectExpenseCategory`, `detectIncomeFromDescription`, all now in `financials.js`) or manually entered fields.

**Every displayed metric carries a computed confidence.** `computeConfidence()` grades on volume and recency and returns `low`/`moderate`/`high` with a reason. Confidence is computed, never hardcoded per metric. Two rules follow from it and must not be quietly relaxed: a metric with insufficient data renders `---`, never `0` (a zero is a claim; an absence is the truth), and `capSeverityForVolume()` prevents a single month of data from ever producing a `critical` severity. The Edge Function receives the confidence and hedges accordingly. The metrics themselves are never stored; every load recomputes them. The data they are computed from is persisted — transactions in the event store, plus `recurring_obligations` and `directives`. **Recurring obligations** (`detectRecurringObligations`) know six cadences: weekly, biweekly, semimonthly, monthly, quarterly, annual. Payroll's ~14-15 day gap fit none of the original four, so a business's largest committed cost was missing; `classifyTwiceMonthly` separates biweekly from semimonthly by whether the payday holds still in the month. Monthly, quarterly and annual obligations step whole months on their typical payday (the most common day across their payments; `day_of_month` 31 means the last day of the month), never a fixed number of days: 30-day steps drifted a day earlier every month and inherited any weekend shift. Descriptions that do not repeat exactly (payroll lines carry a new reference number every run) are regrouped with digits removed, but `normalizeDescription` itself must not change: it also feeds the duplicate-upload hash. The database's `recurring_obligations_cadence_check` must list every cadence the detector can return, and must be widened before the code that returns a new one ships, because the browser upserts all obligations in one request and one rejected value drops them all. **Hiring Capacity** is monthly profit over the last 3 complete calendar months, less loan repayments and owner withdrawals, times (1 − the mode's safety share), and zero while the business burns: the largest fully-loaded monthly cost the business's own profit carries. It replaced a `hireReady` flag that compared the whole period's profit to a fixed $25k/month hire; do not reintroduce a fixed salary, and there is deliberately no "hire now" directive. A specific salary is tested with `checkAffordability()`. "Safe Mode" vs. "Growth Mode" reserve percentages (30%/20% vs. 25%/10%) are hardcoded constants applied uniformly, not derived from the business's actual data. Period profit less those reserves is the `free` metric, shown as **Profit after reserves**. It was labelled "True Free Cash" until November 2026, which wrongly suggested a cash balance; the stored directive rule `negative_free_cash` and target metric `free` keep their names so the decision history still matches. **Growth score** is 50 + (rateScore − 50) × (0.6 + 0.4 × consistency), where rateScore is 50 + 3 per percent of monthly growth. Growth is measured between levels (`growthReading()`, D11): the average of the latest block of months against the block before (3 against 3 with six months, 2 against 2 with four or five), as a monthly rate, and only when the last three changes all moved that way; otherwise the rate is 0 and the projection is the latest block's average with no growth. Averaging percentage changes called a business that swung between 10,000 and 20,000 "Accelerating". Flat revenue is always 50 ("Flat"). There is no Sovereignty index: it was removed (D12), because with bank uploads it was net margin under bands that called a 25% margin "Critical". **Concentration** is not shown when payer names cannot be read (under 60%), when payment processors or marketplaces (`isAggregatorCounterparty`, including Yoco, PayFast, iKhokha, Ozow, Paystack, Takealot) carry half or more of revenue, or when no client is named; names that only say how money arrived ("cash deposit", "eft 4471") count as unread (`isGenericCounterparty`), and "fewer than three clients" needs no processor money.

**Every amount has a currency, and amounts are never converted.** `profiles.base_currency` (USD or ZAR, listed in `SUPPORTED_CURRENCIES` in `financials.js`) is the currency a business keeps its books in. Like `plan` it has no default, because a default would label a South African business as USD; the app asks before the first import. Transactions, uploads, recurring obligations and directives each store their own ISO code (migration `20261101060729`; a `fill_currency` trigger labels rows from a client that sends none). Metrics are computed only from transactions in the base currency (`partitionByCurrency`): rows in another currency are kept, listed under Transactions, and counted in a notice, never added in. There is no exchange-rate conversion; adding it needs a named rate source, with the rate, its date and the original amount stored, and the founder's approval. `fmt(n, currency)` and `fmtCompact` take the currency, and every call in `App.jsx` must pass it: the USD default exists only so older callers keep their meaning, and it would silently print "$" beside rand. Amounts are read by `parseAmount()`, which decides comma or dot decimals once per column (`detectDecimalStyle`) and understands Cr/Dr, parentheses, a trailing minus, symbols and ISO codes, plus a separate Dr/Cr column (`DIRECTION_HEADERS`) beside an unsigned Amount. It replaced a regex that read "1 234,56" as 123456 and "1,000.00 Dr" as 0. A column whose values fit both readings keeps the dot reading, so US files parse exactly as before. To add a currency, widen `profiles_base_currency_check` first, then add it to `SUPPORTED_CURRENCIES` with its locale and `materialMove` (the smallest burn change worth a trend, in that currency's own units; it is a materiality judgment, not an exchange rate). A mislabelled upload is corrected through the `relabel_upload_currency` RPC, because transactions deliberately have no update policy. Command Ledger's own prices are US dollars and are written "US$"; that is separate from a customer's business currency, and PayPal checkout stays USD.

**AI advisor: the evidence contract (Project 3, contract 2).** The browser builds the advisor's evidence with `buildAdvisorEvidence()` (`financials.js`): every figure the engine computes, each with its label, the value as the dashboard shows it (`display`), its period, its status (`available`, `estimate`, `held`, `unavailable`; a held or unavailable item has no value), confidence, reason and definition, plus the engine's ordered findings (with the evidence each rests on), the holds, D1's window, the affordability result when the founder tests a cost, bills, past directives and the founder's question. It sends no transactions and no client names. `supabase/functions/_shared/advisor-contract.ts` is the one place the contract lives: `sanitizeEvidence()` rebuilds what the browser sends field by field; the prompt and `RESPONSE_SCHEMA` ask for JSON through `output_config.format`; `validateAdvisorReply()` removes any point that quotes a figure the evidence does not hold (numbers are compared at the precision written, in any separator style), cites evidence that does not exist, calls a tax estimate owed, promises an outcome, claims authority, treats Profit after reserves as cash, recommends spending without a passing affordability check, contradicts the check (a pass denied, or a held check answered yes or no), or raises an alarm the engine does not; caps each point's confidence at its evidence; replaces a summary that calls a problem fine; and replaces the whole reply with `engineBrief()`, the engine's own reading, labelled as such, when no point survives or the reply passes over the most serious finding. Status and risk always come from the engine, and `guardVerificationClaims` runs on every string. While money in is unconfirmed or VAT is unanswered (`MODEL_HOLDS`) the model is never called, by the browser or the server: the engine's reading explains the hold. The Advisor screen shows each point with the evidence it rests on, taken from the evidence the browser sent, never from the model's text. The function still answers the older body below for browsers on the previous site, so deploy the function before the website. Earlier (legacy) behaviour: `Dashboard` called `supabase.functions.invoke("analyze-finances")`, which hits `supabase/functions/analyze-finances/index.ts` — a Supabase Edge Function that sends the computed metrics to the Anthropic Messages API and returns a structured recommendation (What Happened / Why / Business Impact / Risk / Action / Expected Outcome / Confidence). The system prompt deliberately **does** hedge on low-confidence input, refuses to call an established seasonal pattern a decline, and caps risk at `Watch` when only one month of data exists — there is a code-level cap enforcing that last rule regardless of what the model returns. Its output is rendered as React text, never `dangerouslySetInnerHTML`, because model output is untrusted content. The brief also carries the cash balance with its date and source, the money kept out of revenue and costs, and the number of partial months; the function accepts the older `trueFreeCash` field name for `profitAfterReserves`. **The model is `claude-opus-5-5`**, moved from Sonnet 4.5 before that retired on 2026-11-30. Thinking is always on, so `output_config.effort` (`medium`) is the control and `max_tokens` (16000) must leave room for thinking as well as the reply; it rejects `temperature`; the reply is read by block `type`, never `content[0]`, because a response can begin with thinking blocks; and `stop_reason` "refusal" is checked before content, with `fallbacks: "default"` (beta `server-side-fallback-2026-07-01`) retrying a declined request on another model server-side. The call is a direct `fetch`, so the function has no SDK dependency, and it gives up after 120 seconds with a plain message. (A duplicate Vercel implementation, `api/analyze-ledger.js`, existed with a different prompt and data contract but was never called by the frontend — it was removed as dead code.)

**Access comes from PayPal's own record, read on the server, by two routes.** `PayModal` creates the subscription client-side (passing `custom_id: userId`) and never writes to the database. `confirm-subscription` is called with the subscription id when PayPal issues it (`register`, recorded in `subscription_checkouts` before the buyer approves) and again on approval (`confirm`); it reads the subscription from PayPal and requires `custom_id` to be the signed-in user. `paypal-webhook` verifies events through PayPal's `/v1/notifications/verify-webhook-signature` API and hands them to `_shared/paypal-events.ts`. Both grant through `applyGrant()` in `_shared/paypal-access.ts`, which needs PayPal to report the subscription ACTIVE and paid (`grantBlock()`: ACTIVE alone is not proof of payment, and an ended subscription is refused even if a late payment event arrives). **A real payment once produced nothing because the webhook could not work and the browser threw the subscription id away:** `PAYPAL_WEBHOOK_ID` held an 80-character value that was not a webhook id, and the REST app that creates subscriptions had no webhook of its own. PayPal delivers subscription events to the webhooks of the app that created them, so one listed only at account level (`anchor_type=ACCOUNT`) receives nothing. An unsigned test request is rejected whether or not the id is right, so that check proved nothing. Every verified event is stored once in `payment_events` by its PayPal event id: a duplicate is skipped, a failure is recorded and answered with 500 so PayPal redelivers, and `needs_review` flags what a person must decide. Reopening the app rechecks open checkouts, so a closed browser still gets access, and Subscribe stays closed until that check has run. Refunds are recorded and flagged, access unchanged. A chargeback sets `plan` null and `status` 'disputed' at once, a renewal cannot lift it, and winning the dispute restores it. A full Diagnostic refund marks the order `refunded`. `payment-admin` and the Payment repair panel in Settings list what needs a person and re-check a subscription with PayPal; both need a row in `app_admins`, which holds the founder's two accounts. Add a row only when the founder names the account, because the panel shows customer emails. **Only the subscription on file decides access.** `profiles.paypal_subscription_id` (migration `20261030183827`, guarded like `plan`/`status`) records which subscription granted the plan; `_shared/subscription-entitlement.ts` decides every event against it. An upgrade creates a second PayPal subscription and nothing cancels the first, so without this the old $99 renewal downgraded Advisory customers and its cancellation revoked paid access. When two live subscriptions exist the newer one wins and the webhook **cancels the older one in PayPal** (`cancelSuperseded`), after first moving the profile to the new subscription so the resulting CANCELLED event cannot revoke access. It cancels only when the kept subscription is `ACTIVE` and both carry the same `custom_id`; otherwise it logs `Customer has two live subscriptions` for a person to resolve, and a failed cancel logs `Could not cancel superseded subscription`. Already-paid periods are never refunded automatically. `PayModal` tells an upgrading customer this before they pay. Apply that migration before deploying the webhook, or every event returns 500 until it exists.

**PayPal plan ids live in exactly one place:** `supabase/functions/_shared/paypal-plans.ts`, imported by both `paypal-webhook` and `plan-pricing`. The browser holds no plan ids. To add, retire or swap a plan, edit only that file and redeploy both functions. Retired plan ids stay mapped until no live subscription remains on them.

**PayPal owns the price; this app only renders it.** When `PayModal` opens it calls the `plan-pricing` Edge Function, which reads the plan's live terms from PayPal — recurring amount, currency, interval, trial cycles and setup fee — and `checkoutBlockReason()` in `financials.js` opens checkout only if **every charge, starting with the first, equals the price shown**. A setup fee always blocks it. A trial cycle blocks it unless the page discloses it as the plan's `intro` (`{ usd, months }` in `PLANS`) and PayPal bills exactly that: one trial cycle, that amount, USD, the plan's interval, that many cycles. A disclosed intro that PayPal no longer bills blocks too, because the page would promise a price nobody is charged. No plan currently has an intro. Tax follows the same rule: a tax PayPal adds on top of each charge (not inclusive) must be disclosed as the plan's `tax` (`{ percent }` in `PLANS`) at the same rate, and a disclosed tax PayPal does not add blocks too (`tax_mismatch`); plan-pricing reports `taxPercent` and `taxInclusive`, and a tax it cannot read blocks as unverified. No plan currently carries a tax: the Command Ledger plan added 15% on top of US$99 (US$113.85 charged against US$99 shown) until the founder had it set to 0% in PayPal on 2026-11-03, and `PLANS.software.tax` was removed in the same change. To charge a tax, set the rate in PayPal and `tax` in `PLANS` together, or checkout blocks; every price display then states it through `taxTerms()`. Blocked checkout shows the customer one neutral message plus an email route, and logs the specific reason to the console. **Never resolve a block by loosening the check** — change the plan in PayPal, or change the page to disclose the terms. PayPal plans *can* be repriced in place (an earlier version of this file said otherwise, which was wrong); because the check is live, an in-place reprice reaches checkout within the function's 5-minute cache without a code change.

**One-time purchases are PayPal orders, not plans.** PayPal plans exist only for subscriptions; a one-time payment is an order carrying its own amount, so whoever creates the order sets the price. The `diagnostic-order` Edge Function therefore creates the order on the server from `DIAGNOSTIC` in `_shared/one-time-products.ts`, and the browser only ever receives an order id. The same function captures the payment and `verifyDiagnosticCapture()` checks the amount, currency and payer before `diagnostic_orders` is updated. That table has no insert/update/delete policies, so only the server can mark an order paid. If the buyer's browser closes between paying and the capture returning, `paypal-webhook` records it from `PAYMENT.CAPTURE.COMPLETED`. **An ambiguous capture outcome must never be reported to the buyer as "not charged"** — a buyer told their payment failed pays again on a new order and is charged twice. Only a PayPal 4xx naming a specific reason counts as no money moved; anything else says "do not pay again". The "credited against your first Advisory month" promise is applied by hand, not automatically.

**Two offers, not three tiers:** `software` (Command Ledger, $99/mo, self-serve; annual $990 is arranged by email because no annual PayPal plan exists) and `advisory` (Command Advisory, US$1,500/mo since 2026-11-03, PayPal plan `P-2X763934UU660913BNLUSB7Q`; six clients at a time; adds monthly data processing, a 60-minute call and a 2 to 4 page board pack every month, a quarterly 12-month forecast, and an email line answered within 24 hours on business days). The US$99 plan includes no calls: email support only, replied to within 2 business days. The US$3,000 plan with its US$1,950 first month (`P-7M170334YK027974RNITP7NY`) is retired and stays mapped to `advisory` in `paypal-plans.ts`. These promises are written in `PLANS`, the FAQ, the Help page and the Terms; change them together. `DIAGNOSTIC` ($750 one-time: twelve months of exports in, within 10 business days a written findings memo with the 3 to 5 decisions that matter most and the money attached to each, plus a 60-minute call; credited against Advisory if the buyer joins within 30 days) is bought through `DiagnosticModal`, reachable from the pricing page, `PaywallGate`, and the software-plan nudge in `Dashboard`. Profiles created under the retired Essentials/Pro/Elite pricing are mapped by `resolvePlanKey()`, so `PLANS[plan]` is never undefined — keep that resolver as long as any legacy row or subscription can exist.

**Edge Function secret naming is non-standard — check before assuming.** The PayPal client secret is stored under `PAYPAL_SECRET_ID`, not the more conventional `PAYPAL_CLIENT_SECRET`. `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are injected automatically into every Edge Function and don't need to be set manually. `PAYPAL_API_BASE` defaults to the PayPal sandbox API if unset — it must be explicitly set to `https://api-m.paypal.com` for the webhook to verify events from a live PayPal app. `PAYPAL_WEBHOOK_ID` is the id of the webhook on the checkout app, 17 upper-case characters, not a client id; the webhook answers 500 and logs it if the value does not look like one.

**Deployment is Vercel**, with `vercel.json` rewriting every path except `/_vercel/` to `index.html` for SPA routing. `/_vercel/` is left alone so Vercel Web Analytics (`/_vercel/insights/script.js`, loaded from `index.html`) answers 404 while Analytics is disabled for the project, instead of index.html arriving as a broken script; enabling Analytics in the Vercel dashboard starts counting with no deploy. Note that Vercel serves an existing static file before applying that rewrite — any file placed at the repo root (as `checkout.html` was, before it was removed as dead/misleading code) is still directly reachable at its own URL regardless of the rewrite rule, even if nothing in the app links to it.

## Development workflow

For any non-trivial feature in this repo, plan before implementing: understand the requirement, inspect the existing architecture, identify affected components and dependencies, identify risks, write an implementation plan, and identify required tests — plus, because this is a financial product, explicitly call out security implications and financial-calculation implications wherever the change touches money, metrics, or user-facing numbers. Implement in small, verifiable steps.

A feature is not complete because it compiles or the happy path ran once. Before reporting it done, run the test suite and linting if configured, inspect the actual diff, exercise the affected workflows, perform a security review, verify calculations, and check responsive/UI behavior where relevant. Completion means functionality, tests, security, UX, edge cases, and regression checks have all been addressed.
