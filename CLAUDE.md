# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the Vite dev server
- `npm run build` — production build to `dist/`
- `npm run preview` — preview a production build locally
- `npm test` — run the Vitest suite once (`vitest run`)

There is a test suite. `src/lib/financials.test.js` covers `src/lib/financials.js` with hand-computed expectations; run it before reporting any calculation change complete. `src/lib/one-time-products.test.js` imports `supabase/functions/_shared/one-time-products.ts` directly — the exact code the Edge Functions run to judge captured money — which works because that module has no imports and no Deno APIs. Keep it that way, or the server's payment checks drop out of test coverage. `src/lib/subscription-entitlement.test.js` does the same for `supabase/functions/_shared/subscription-entitlement.ts`, under the same rule. `src/lib/currency.test.js` covers money formatting, amount parsing (comma decimals, Cr/Dr, currency markers) and mixed-currency files; `src/lib/workspace.test.js` also reads `App.jsx` and fails if any `fmt(`/`fmtCompact(` call omits its currency. There is still no lint script; if you add one, wire it into `package.json` and update this section. Test settings live under `test` in `vite.config.js`: `src/lib/test-setup.js` warms up `Intl` and WebCrypto before any test is timed, and `testTimeout` is 30s. Both exist because the first test in a worker absorbed several seconds of runtime start-up on slow 2-core machines and failed intermittently against Vitest's 5s default (a plain `fmt(1250)` once took 7.4s). Don't remove either as clutter, and don't paper over a new timeout with a command-line flag.

**`xlsx` is installed from the vendor's CDN, not the npm registry.** SheetJS stopped publishing to npm after 0.18.5, which carries an unpatched prototype-pollution and a ReDoS advisory, so `package.json` pins `https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz`. A fresh `npm install` therefore needs `cdn.sheetjs.com` to be reachable. Do not "fix" this back to a registry range — that silently reintroduces both advisories.

Supabase Edge Functions are deployed with the Supabase CLI via `npx` (it isn't installed globally in this repo):

```
npx supabase functions deploy <function-name> --project-ref rjecagelwzorklmnscrr
npx supabase secrets list --project-ref rjecagelwzorklmnscrr
npx supabase secrets set KEY=value --project-ref rjecagelwzorklmnscrr
```

Database schema lives in `supabase/migrations/` and is applied with `npx supabase db push --linked`. `npx supabase migration list --linked` compares local to remote. The `profiles` table predates these migrations and was managed by hand on the remote project; its entitlement columns (`status`, `updated_at`) and its plan guard now live in migration `20260913010000`. **`profiles.plan` has no default and must never be given one** — it carried `DEFAULT 'essentials'` until `20260913020000`, which entitled every inserted row that did not name a plan. The guard trigger `guard_profiles_plan_status` fires `BEFORE INSERT OR UPDATE` and resets `plan`/`status` for the `anon` and `authenticated` roles; only `service_role` (the webhook) and direct database connections can set them.

**Code was written against `profiles` columns that did not exist, and nothing noticed for months.** The webhook wrote `status` and `updated_at`, the AI advisor selected `status`, and sign-up wrote `updated_at` — none of which the table had. PostgREST rejected every one of those requests, so no subscription could grant access, the advisor refused every user, and new profile rows were never created. Two lessons follow. **Before shipping code that reads or writes a column, confirm the column exists** (`information_schema.columns`). And **never discard a Supabase `error`** — each of these failures was silent only because the error was ignored or a fallback hid it. A third: **PostgREST returns at most 1,000 rows per request and does not say so.** Reading transactions in one request gave any business with more than 1,000 in the period only its oldest 1,000, silently dropping the latest months; `selectAll()` in `App.jsx` pages through every row, and any new bulk read must use it.

Two CLI quirks worth knowing: there is **no `functions logs` subcommand**, and `secrets list` prints digests only, never plaintext.

## Architecture

**The entire application is one file.** `src/main.jsx` just mounts `src/App.jsx`, which contains the marketing site, auth flow, dashboard, all React components, and all CSS (as an inline template-literal string assigned to `CSS`) — around 2,800 lines. **A stray backtick anywhere inside the `CSS` template literal terminates the string and breaks the build**, so never use backticks in its comments. **Every class in `CSS` is global**, so a new class can collide with a marketing-site rule: a KPI tile once used `hero` and inherited the marketing hero's `min-height:100vh`. Grep for an existing `.name{` before introducing a class.

**Design follows `DESIGN.md` and `UX-CONTRACT.md`; read both before any visual change.** Colour tokens are defined once in the `:root` block at the top of `CSS`, sampled from the brand mark, and the `C` object maps each to `var(--token)` for inline styles, so no component hardcodes a colour. **`assets/Logo.png` is the final brand asset**: never crop, recolour, redraw or generate alternatives; `public/brand/` and the favicons are the same image scaled only, and `BrandMark` picks the right copy. Public-site classes use the `mk-` prefix. No em or en dashes in any user-facing copy.

The one exception to the single-file rule is `src/lib/financials.js`, which holds every pure calculation and parsing function. New financial logic belongs there, not in `App.jsx`, because that is the only part of the codebase under test. There is no router; navigation is a single `appState` state machine in the top-level `App()` component (`loading` → `marketing` / `login` / `dashboard` / `terms` / `privacy`), and `Dashboard` vs. `PaywallGate` is chosen based on whether `profile.plan` is set. Inside the signed-in workspace, `Dashboard` is an app shell (sticky header with search, alerts, period selector and account menu; a sidebar that becomes a drawer below 960px) with nine sections, each at its own path (`SECTIONS` in `App.jsx`: `/dashboard`, `/transactions`, `/financials`, `/advisor`, `/reports`, `/decisions`, `/forecasts`, `/settings`, `/help`). `useSection()` reads the path on load, `pushState`s on navigation and listens for `popstate`; there is no router dependency. A signed-out visitor on a workspace path is sent to `/`. Two public pages have their own paths, `/terms` and `/privacy` (`LEGAL_PATHS`), so search engines can index them and payment providers can link to them; `App` writes each page's `<title>` and canonical link after rendering, because the single `index.html` cannot know the path (do not put a static canonical back in `index.html`: it would point `/terms` at the home page). `vercel.json` sends `X-Robots-Tag: noindex` on every extension-less path except `/`, `/terms` and `/privacy`, which keeps the workspace and every unknown path (the SPA rewrite answers those with 200) out of search. A new public page needs its path excluded from that rule and added to `public/sitemap.xml`. `Dashboard` loads data and derives every metric once, then hands sections a single `ctx` object, so a number shown on two pages cannot disagree. Header search (`searchWorkspace`), the alerts bell (`buildAlerts`) and the Reports CSV (`buildReportCsv`) are pure functions in `financials.js`, tested in `src/lib/workspace.test.js`.

**Auth and plan-gating run through Supabase.** The Supabase client is created at module scope with `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`. On sign-in, `loadProfile()` reads (or upserts) a row in the `profiles` table; a falsy `profile.plan` routes the user to `PaywallGate` instead of `Dashboard`. Access control is entirely driven by `profiles.plan` — there is no separate entitlements table.

**Financial metrics are computed client-side, not stored.** `computeMetrics()` in `src/lib/financials.js` derives margin, burn runway, LTV:CAC, break-even, a 90-day projection, a trend-aware composite risk score, growth scoring with a seasonality override, revenue concentration by counterparty, and forward obligations — from either parsed rows (`parseAnyCSV`, `parseTransactions`, `detectExpenseCategory`, `detectIncomeFromDescription`, all now in `financials.js`) or manually entered fields.

**Every displayed metric carries a computed confidence.** `computeConfidence()` grades on volume and recency and returns `low`/`moderate`/`high` with a reason. Confidence is computed, never hardcoded per metric. Two rules follow from it and must not be quietly relaxed: a metric with insufficient data renders `---`, never `0` (a zero is a claim; an absence is the truth), and `capSeverityForVolume()` prevents a single month of data from ever producing a `critical` severity. The Edge Function receives the confidence and hedges accordingly. The metrics themselves are never stored; every load recomputes them. The data they are computed from is persisted — transactions in the event store, plus `recurring_obligations` and `directives`. **Recurring obligations** (`detectRecurringObligations`) know six cadences: weekly, biweekly, semimonthly, monthly, quarterly, annual. Payroll's ~14-15 day gap fit none of the original four, so a business's largest committed cost was missing; `classifyTwiceMonthly` separates biweekly from semimonthly by whether the payday holds still in the month. Monthly, quarterly and annual obligations step whole months on their typical payday (the most common day across their payments; `day_of_month` 31 means the last day of the month), never a fixed number of days: 30-day steps drifted a day earlier every month and inherited any weekend shift. Descriptions that do not repeat exactly (payroll lines carry a new reference number every run) are regrouped with digits removed, but `normalizeDescription` itself must not change: it also feeds the duplicate-upload hash. The database's `recurring_obligations_cadence_check` must list every cadence the detector can return, and must be widened before the code that returns a new one ships, because the browser upserts all obligations in one request and one rejected value drops them all. **Hiring Capacity** is average monthly profit times (1 − the mode's safety share): the largest fully-loaded monthly cost the business's own profit carries. It replaced a `hireReady` flag that compared the whole period's profit to a fixed $25k/month hire; do not reintroduce a fixed salary, and there is deliberately no "hire now" directive. A specific salary is tested with `checkAffordability()`. "Safe Mode" vs. "Growth Mode" reserve percentages (30%/20% vs. 25%/10%) are hardcoded constants applied uniformly, not derived from the business's actual data.

**Every amount has a currency, and amounts are never converted.** `profiles.base_currency` (USD or ZAR, listed in `SUPPORTED_CURRENCIES` in `financials.js`) is the currency a business keeps its books in. Like `plan` it has no default, because a default would label a South African business as USD; the app asks before the first import. Transactions, uploads, recurring obligations and directives each store their own ISO code (migration `20261101060729`; a `fill_currency` trigger labels rows from a client that sends none). Metrics are computed only from transactions in the base currency (`partitionByCurrency`): rows in another currency are kept, listed under Transactions, and counted in a notice, never added in. There is no exchange-rate conversion; adding it needs a named rate source, with the rate, its date and the original amount stored, and the founder's approval. `fmt(n, currency)` and `fmtCompact` take the currency, and every call in `App.jsx` must pass it: the USD default exists only so older callers keep their meaning, and it would silently print "$" beside rand. Amounts are read by `parseAmount()`, which decides comma or dot decimals once per column (`detectDecimalStyle`) and understands Cr/Dr, parentheses, a trailing minus, symbols and ISO codes, plus a separate Dr/Cr column (`DIRECTION_HEADERS`) beside an unsigned Amount. It replaced a regex that read "1 234,56" as 123456 and "1,000.00 Dr" as 0. A column whose values fit both readings keeps the dot reading, so US files parse exactly as before. To add a currency, widen `profiles_base_currency_check` first, then add it to `SUPPORTED_CURRENCIES` with its locale and `materialMove` (the smallest burn change worth a trend, in that currency's own units; it is a materiality judgment, not an exchange rate). A mislabelled upload is corrected through the `relabel_upload_currency` RPC, because transactions deliberately have no update policy. Command Ledger's own prices are US dollars and are written "US$"; that is separate from a customer's business currency, and PayPal checkout stays USD.

**AI advisor: one live implementation.** `Dashboard` calls `supabase.functions.invoke("analyze-finances")`, which hits `supabase/functions/analyze-finances/index.ts` — a Supabase Edge Function that sends the computed metrics to the Anthropic Messages API and returns a structured recommendation (What Happened / Why / Business Impact / Risk / Action / Expected Outcome / Confidence). The system prompt deliberately **does** hedge on low-confidence input, refuses to call an established seasonal pattern a decline, and caps risk at `Watch` when only one month of data exists — there is a code-level cap enforcing that last rule regardless of what the model returns. Its output is rendered as React text, never `dangerouslySetInnerHTML`, because model output is untrusted content. (A duplicate Vercel implementation, `api/analyze-ledger.js`, existed with a different prompt and data contract but was never called by the frontend — it was removed as dead code.)

**PayPal subscriptions activate through a webhook, not the browser.** `PayModal` in `App.jsx` creates a PayPal subscription client-side (passing `custom_id: userId` so the backend can identify the user) but does **not** write to the database on approval — that comment is explicit in the code. The actual plan/status update happens in `supabase/functions/paypal-webhook/index.ts`, which verifies the event via PayPal's `/v1/notifications/verify-webhook-signature` API and then updates `profiles.plan` / `profiles.status` based on the event type (`BILLING.SUBSCRIPTION.ACTIVATED` grants access, `CANCELLED`/`EXPIRED` revokes it, `SUSPENDED` records a grace period, `PAYMENT.SALE.COMPLETED`/`PAYMENT.CAPTURE.COMPLETED` keep renewals in sync). Grant events throw when no profile row matches, so the webhook returns 500 and PayPal redelivers instead of acknowledging a paid subscription it could not apply. **Only the subscription on file decides access.** `profiles.paypal_subscription_id` (migration `20261030183827`, guarded like `plan`/`status`) records which subscription granted the plan; `_shared/subscription-entitlement.ts` decides every event against it. An upgrade creates a second PayPal subscription and nothing cancels the first, so without this the old $99 renewal downgraded Advisory customers and its cancellation revoked paid access. When two live subscriptions exist the newer one wins and the webhook **cancels the older one in PayPal** (`cancelSuperseded`), after first moving the profile to the new subscription so the resulting CANCELLED event cannot revoke access. It cancels only when the kept subscription is `ACTIVE` and both carry the same `custom_id`; otherwise it logs `Customer has two live subscriptions` for a person to resolve, and a failed cancel logs `Could not cancel superseded subscription`. Already-paid periods are never refunded automatically. `PayModal` tells an upgrading customer this before they pay. Apply that migration before deploying the webhook, or every event returns 500 until it exists.

**PayPal plan ids live in exactly one place:** `supabase/functions/_shared/paypal-plans.ts`, imported by both `paypal-webhook` and `plan-pricing`. The browser holds no plan ids. To add, retire or swap a plan, edit only that file and redeploy both functions. Retired plan ids stay mapped until no live subscription remains on them.

**PayPal owns the price; this app only renders it.** When `PayModal` opens it calls the `plan-pricing` Edge Function, which reads the plan's live terms from PayPal — recurring amount, currency, interval, trial cycles and setup fee — and `checkoutBlockReason()` in `financials.js` opens checkout only if **every charge, starting with the first, equals the price shown**. A trial or setup fee blocks it even when it favours the customer, because the page does not disclose it. Blocked checkout shows the customer one neutral message plus an email route, and logs the specific reason to the console. **Never resolve a block by loosening the check** — change the plan in PayPal, or change the page to disclose the terms. PayPal plans *can* be repriced in place (an earlier version of this file said otherwise, which was wrong); because the check is live, an in-place reprice reaches checkout within the function's 5-minute cache without a code change.

**One-time purchases are PayPal orders, not plans.** PayPal plans exist only for subscriptions; a one-time payment is an order carrying its own amount, so whoever creates the order sets the price. The `diagnostic-order` Edge Function therefore creates the order on the server from `DIAGNOSTIC` in `_shared/one-time-products.ts`, and the browser only ever receives an order id. The same function captures the payment and `verifyDiagnosticCapture()` checks the amount, currency and payer before `diagnostic_orders` is updated. That table has no insert/update/delete policies, so only the server can mark an order paid. If the buyer's browser closes between paying and the capture returning, `paypal-webhook` records it from `PAYMENT.CAPTURE.COMPLETED`. **An ambiguous capture outcome must never be reported to the buyer as "not charged"** — a buyer told their payment failed pays again on a new order and is charged twice. Only a PayPal 4xx naming a specific reason counts as no money moved; anything else says "do not pay again". The "credited against your first Advisory month" promise is applied by hand, not automatically.

**Two offers, not three tiers:** `software` (Command Ledger, $99/mo, self-serve; annual $990 is arranged by email because no annual PayPal plan exists) and `advisory` (Command Advisory, $3,000/mo, 6 seats, adds the monthly call and board report). `DIAGNOSTIC` ($750 one-time) is bought through `DiagnosticModal`, reachable from the pricing page, `PaywallGate`, and the software-plan nudge in `Dashboard`. Profiles created under the retired Essentials/Pro/Elite pricing are mapped by `resolvePlanKey()`, so `PLANS[plan]` is never undefined — keep that resolver as long as any legacy row or subscription can exist.

**Edge Function secret naming is non-standard — check before assuming.** The PayPal client secret is stored under `PAYPAL_SECRET_ID`, not the more conventional `PAYPAL_CLIENT_SECRET`. `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are injected automatically into every Edge Function and don't need to be set manually. `PAYPAL_API_BASE` defaults to the PayPal sandbox API if unset — it must be explicitly set to `https://api-m.paypal.com` for the webhook to verify events from a live PayPal app.

**Deployment is Vercel**, with `vercel.json` rewriting every path except `/_vercel/` to `index.html` for SPA routing. `/_vercel/` is left alone so Vercel Web Analytics (`/_vercel/insights/script.js`, loaded from `index.html`) answers 404 while Analytics is disabled for the project, instead of index.html arriving as a broken script; enabling Analytics in the Vercel dashboard starts counting with no deploy. Note that Vercel serves an existing static file before applying that rewrite — any file placed at the repo root (as `checkout.html` was, before it was removed as dead/misleading code) is still directly reachable at its own URL regardless of the rewrite rule, even if nothing in the app links to it.

## Development workflow

For any non-trivial feature in this repo, plan before implementing: understand the requirement, inspect the existing architecture, identify affected components and dependencies, identify risks, write an implementation plan, and identify required tests — plus, because this is a financial product, explicitly call out security implications and financial-calculation implications wherever the change touches money, metrics, or user-facing numbers. Implement in small, verifiable steps.

A feature is not complete because it compiles or the happy path ran once. Before reporting it done, run the test suite and linting if configured, inspect the actual diff, exercise the affected workflows, perform a security review, verify calculations, and check responsive/UI behavior where relevant. Completion means functionality, tests, security, UX, edge cases, and regression checks have all been addressed.
